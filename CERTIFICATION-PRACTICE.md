# SAP CAP Hands-On Certification Practice Plan

This plan is designed for a **performance-based exam**: you must be able to build and troubleshoot, not merely recognize terminology.

> Always verify the current exam format and scope on the official SAP certification page before booking. Certification content can change faster than a repository.

## Readiness rule

You are not ready because you can follow this repository. You are ready when you can rebuild the important parts in a blank project, under time pressure, while explaining why each decision is correct.

## Skills matrix

Rate each item from 0 to 3:

- **0** — I do not understand it.
- **1** — I understand it when reading.
- **2** — I can build it with documentation.
- **3** — I can build and debug it from a blank project.

## What this repository cannot replace

A local repository cannot fully simulate:

- SAP Business Application Studio setup and dev-space behavior
- BTP entitlements, service instances, role collections, and trust configuration
- Real XSUAA token flows
- HANA Cloud/HDI deployment and troubleshooting
- Real destinations and S/4HANA connectivity
- SAP Build Work Zone content configuration
- The exact tasks and constraints of the current certification exam

Use SAP's official learning journey and practice system for those skills.

## Four-stage learning method

### Stage 1 — Read and trace

Read files in this order:

1. `db/schema.cds`
2. `srv/learning-service.cds`
3. `srv/learning-service.js`
4. `srv/admin-service.cds`
5. `srv/admin-service-ui.cds`
6. `xs-security.json`
7. `mta.yaml`
8. `DEPLOYMENT.md`

For every file, answer:

- What is generated by CAP?
- What is custom code?
- What runs at design time, build time, or runtime?
- What would break if this file were removed?

### Stage 2 — Execute and observe

Run:

```bash
npm install
npm run watch
```

Then complete every request in `test/certification-drills.http`. Do not just check that it works; inspect:

- HTTP method and URL
- status code
- request and response headers
- OData payload shape
- authentication role
- server log
- generated `$metadata`

### Stage 3 — Modify without copying

Complete these changes using documentation but without copying existing code:

1. Add `Categories` and associate Products to it.
2. Add a mandatory `salesOrganization` field to Orders.
3. Add an `approve` bound action restricted to Admin.
4. Reject submit when stock is insufficient.
5. Decrease stock in the same transaction as submit.
6. Add row-level authorization for orders created by the current user.
7. Add a second localized field and Indonesian data.
8. Add an ETag to Customers and prove stale updates fail.
9. Add a Fiori value-help annotation for Customers.
10. Add one remote read-only service projection.

### Stage 4 — Rebuild under time pressure

Create a blank folder and complete the following simulation.

## 120-minute mock practical exam

### Task 1 — Initialize the project (10 minutes)

Create a Node.js CAP project and configure SQLite for development.

Acceptance criteria:

- `cds watch` starts successfully.
- The root page lists your service.
- `$metadata` is reachable.

### Task 2 — Model the domain (20 minutes)

Create:

- `Customers`
- `Products`
- `Orders`
- `OrderItems`

Requirements:

- UUID keys
- managed fields
- Customer–Order association
- Order–Items composition
- localized product description
- enum order status

### Task 3 — Expose the service (15 minutes)

Expose projections rather than persistence entities directly. Make Products read-only for ordinary users and Orders editable for an Editor role.

### Task 4 — Implement business logic (25 minutes)

Implement:

- validation before create
- backend price lookup
- line and header total calculation
- bound submit action
- low-stock function
- transaction-safe stock update

### Task 5 — Add enterprise behavior (20 minutes)

Add:

- ETag concurrency
- draft-enabled admin service
- one Fiori LineItem annotation
- localized annotation labels

### Task 6 — Test (15 minutes)

Write tests for:

- valid deep insert
- invalid quantity
- forbidden update
- localized read

### Task 7 — Explain deployment (15 minutes)

Without deploying, explain or sketch:

- CAP service module
- HANA/HDI deployer
- XSUAA resource
- destination/remote service
- MTA build and CF deployment
- role collection assignment

## Debugging drills

Break the project deliberately and diagnose it:

1. Misspell an entity name in a projection.
2. Use an association where composition is required.
3. Remove an authorization role from the mock user.
4. Send a stale ETag.
5. Use an unknown product in a deep insert.
6. Remove the HANA resource from `mta.yaml`.
7. Configure the wrong destination name.
8. Override `READ` but forget to return data.
9. Query a virtual property in the database layer.
10. Use a V2-style URL/payload assumption against OData V4.

For each failure, record:

- symptom
- root cause
- tool/log used
- fix
- prevention

## Oral explanation prompts

Practice answering each in under 90 seconds:

1. Why does CAP use convention over configuration?
2. Why separate persistence models and service projections?
3. When is composition preferable to association?
4. What is generated from a localized field?
5. How does CAP enforce optimistic concurrency?
6. What is the difference between `before`, `on`, and `after`?
7. Why use `cds.tx(req)`?
8. Why must authorization be enforced in CAP rather than only UI5?
9. What is the difference between action, function, and event?
10. What does draft solve for Fiori applications?
11. How does CAP consume an S/4 API through a destination?
12. How do SQLite and HANA profiles differ?
13. What does the HDI deployer do?
14. What belongs in `xs-security.json`?
15. When should you choose RAP instead of CAP?

## Weekly plan

### Week 1 — CDS and generic services

- Rebuild the domain twice.
- Practice associations, compositions, aspects, enums, localization.
- Use `$metadata`, `$select`, `$filter`, `$expand`, paging, and CRUD.

### Week 2 — Logic, security, and tests

- Build handlers from memory.
- Practice transactions, actions, functions, events, ETags, roles.
- Write unit and integration tests.

### Week 3 — Fiori elements and integration

- Build a draft-enabled service.
- Create UI annotations and a Fiori elements app in BAS.
- Import and consume a remote service through a destination.

### Week 4 — BTP and mock exams

- Deploy to HANA/Cloud Foundry.
- Configure XSUAA roles and role collections.
- Inspect logs and service bindings.
- Complete at least three timed blank-project simulations.

## Final readiness checklist

Book the exam only when most answers are “yes”:

- Can I initialize a CAP project without following a tutorial line by line?
- Can I model header–item ownership correctly?
- Can I inspect `$metadata` to debug naming and navigation?
- Can I implement and test custom handlers?
- Can I explain and demonstrate authorization?
- Can I use an ETag and explain why a stale update fails?
- Can I create a draft-enabled service and basic UI annotations?
- Can I consume a remote service conceptually and in a BTP practice system?
- Can I build and deploy an MTA to Cloud Foundry/HANA?
- Can I recover from errors using logs and documentation under time pressure?
